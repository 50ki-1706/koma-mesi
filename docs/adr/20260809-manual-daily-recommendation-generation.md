# ADR: 手動APIから開始する日次推薦生成

- **Status:** Accepted
- **Date:** 2026-08-09

## Context

日次推薦スキーマへ、大学から徒歩で昼食に行ける店舗を保存する処理がまだ存在しない。最終的には日本時間の毎日11時にCronから生成するが、定期実行、Swagger、フロントエンド用モックを同時に実装すると、推薦ロジックとAPI契約の検証が難しくなる。

昼休みは50分、食事時間は30分、徒歩速度は1分80mとする。往復移動に使える20分の半分である10分から、検索上限を片道800mとする。推薦結果は3カテゴリを選び、カテゴリごとにnear・middle・farから1店舗ずつ、合計9店舗とする。

## Decision

- 最初の入口として、ログインユーザーが手動実行できるoRPCの`recommendation.generate` procedureを追加する。
- procedureは任意の`targetDate`をZodで検証し、`userId`は入力ではなく認証セッションから取得する。日付を省略した場合は日本時間の当日を使う。
- 推薦生成ユースケースはoRPCから分離し、後からCronも同じ処理を呼べるようにする。
- 昼食向けカテゴリはホットペッパー由来の11カテゴリに限定し、固定の変換表でGoogle Placesのprimary typeへ対応付ける。
- 11カテゴリを重複なしでランダムに並べ、Google Nearby Searchをカテゴリごとに最大1回実行する。徒歩経路800m以内で、他カテゴリの選出店舗とも重複しない候補が3件未満なら、そのカテゴリを除外して次を検索する。
- 有効候補を徒歩経路距離順にnear・middle・farへ均等分割し、各グループから1店舗をランダムに選ぶ。3カテゴリが揃った時点で検索を終了する。
- Nearby Searchでは最大20候補のPlace IDと徒歩経路だけを取得し、選出後、DBに存在しない店舗だけPlace Detailsを取得する。
- 選出店舗は`googlePlaceId`で既存店舗と照合し、店舗、任意の料金レンジ、カテゴリ、推薦9件を保存してバッチを`completed`にする。生成途中の失敗はバッチを`failed`にする。
- Google Placesの写真は取得も保存も行わない。写真の取得・更新方式はGoogleの利用規則を確認して別途決定する。
- Cron登録、OpenAPI・Swagger、API契約に沿ったモックデータ、フロントエンド接続は後続の作業とする。

## Consequences

- 手動APIで推薦生成、DB保存、レスポンス契約を先に検証でき、Cronは同じユースケースを再利用できる。
- 通常のNearby Searchは3回だが、候補不足カテゴリを除外した場合は採用カテゴリが3つ揃うまで呼び出し回数が増える。同一カテゴリを再検索することはない。
- 同一ユーザー・同一対象日の既存バッチがある場合は重複生成せず、APIは競合として扱う。
- 保存済み店舗はPlace Detailsを再取得しない。Google由来情報の定期更新と保持期間は、本番運用前に別の設計判断として追加する必要がある。
- 全カテゴリを調べても3カテゴリを確保できない場合は、9店舗未満を保存せずバッチを`failed`にする。
