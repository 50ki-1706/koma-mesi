# ADR: 日次推薦モデルを推薦一覧機能の正とする

- **Status:** Accepted
- **Date:** 2026-08-08

## Context

`main` とのマージにより、推薦データについて異なる2つのモデルが同時に存在する状態になった。

- `genre` と `recommendation` を使い、`is_featured` でジャンルごとの1店舗を選ぶモデル
- `recommendation_batches`、`recommendation_categories`、`recommendations`、`restaurants` を使い、ユーザーと対象日ごとに3カテゴリ・各3店舗を保持するモデル

後者は Vercel Cron による日次推薦、ユーザー単位の対象日管理、near / middle / far の距離グループ、店舗マスタの再利用という現在の要件を反映している。一方、前者を前提にした一覧APIと画面は、後者のスキーマと接続できず型検査に失敗していた。

## Decision

2026-08-08の「推薦データを Turso/SQLite の正規化テーブルで保持する」ADRで定義した日次推薦モデルを、推薦一覧機能の正とする。

- 2026-08-07の「飲食店レコメンド機能のデータモデル」で採用した `genre`、単数形の `recommendation`、`is_featured` モデルは使用しない
- 推薦一覧APIは、ログイン中ユーザーについて日本時間の当日を対象に、`completed` バッチの店舗をカテゴリ選択順・店舗表示順で返す
- 徒歩時間は保存せず、保存済みの距離と80m/分の歩行速度から画面表示時に算出する
- 店舗写真や価格の仮データは返さない。写真取得は `google_place_id` を使うGoogle Places連携の実装時に追加する
- 店舗詳細への暫定的な導線には `google_place_id` を使ったGoogle Maps URLを使用する

本ADRは2026-08-07の推薦モデルに関する決定を置き換える。過去のADRは判断履歴として変更せず保持する。

## Consequences

- DBスキーマ、API、推薦画面が同じ日次推薦モデルを参照し、マージ後の型不整合が解消される
- ユーザーは当日の完了済み推薦だけを取得し、最大9店舗を決められた順序で閲覧できる
- Google Places APIによる写真取得は別実装が必要で、それまでは写真の代わりにプレースホルダーを表示する
- 過去の `genre` / `recommendation` 用マイグレーションは採用せず、日次推薦モデルのマイグレーション1本に統一する
